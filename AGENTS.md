# TwitchDownloader

TwitchDownloader — консольное приложение на C# для мониторинга Twitch-каналов и скачивания трансляций через Telegram-бота. В репозитории есть legacy-версия на .NET 8 и основная кроссплатформенная версия на .NET 10, которая использует `yt-dlp`, `ffmpeg` и поддерживает Docker.

## База знаний — Obsidian

Постоянная память проекта находится в `Obsidian/TwitchDownloaderVault/`.

| Путь | Назначение |
|------|-----------|
| `Obsidian/TwitchDownloaderVault/Index.md` | Главная навигация и правила обновления |
| `Obsidian/TwitchDownloaderVault/Архитектура.md` | Стек, компоненты, сквозные потоки и расширение |
| `Obsidian/TwitchDownloaderVault/modules/v1-overview.md` | Legacy-контур `TwitchDownloader.CLI` |
| `Obsidian/TwitchDownloaderVault/modules/v2-*.md` | Компоненты `TwitchDownloader2.CLI` |
| `Obsidian/TwitchDownloaderVault/api/*.md` | Telegram, внешние CLI и Docker-интерфейсы |
| `Obsidian/TwitchDownloaderVault/Deployment/updatetwitch.md` | Серверный updater `scripts/updatetwitch` |
| `Obsidian/TwitchDownloaderVault/structure/*.md` | Структура репозитория и точки входа |

В начале работы прочитай `Index.md`, затем переходи по wikilinks к затронутому компоненту.

## Правила обновления Obsidian

- Изменилась функциональность файла или метода → обнови заметку компонента на месте.
- Добавлен новый файл или компонент → создай/дополни заметку в фактическом домене и добавь ссылку в `Index.md`.
- Изменилась архитектура, зависимости или конфигурация → обнови `Архитектура.md`.
- Удалённый метод помечай как `~~methodName~~ (удалён: [дата])`; новый метод добавляй в таблицу.
- Используй формат `methodName(param: Type): ReturnType — [одна строка что делает]`.
- Новые changelog-файлы не создавай: историю изменений ведёт git.

## Правила чтения файлов проекта

Для исследования структуры используй `rg --files` с исключением `.git`, `Obsidian`, `bin`, `obj` и других артефактов сборки. Для большого репозитория сначала используй Explore-субагента с моделью haiku; для этого небольшого репозитория достаточно точечного чтения solution, README, csproj, исходников и конфигурации. Перед правкой читай конкретный файл напрямую; заметки Obsidian также читай напрямую и дополняй, а не переписывай без необходимости.

## Быстрые команды

```bash
dotnet build TwitchDownloader.sln -p:EnableWindowsTargeting=true
dotnet run --project TwitchDownloader2.CLI/TwitchDownloader2.CLI.csproj
docker compose -f docker/docker-compose.yml up -d --build
docker compose -f docker/docker-compose.yml logs -f
docker compose -f docker/docker-compose.yml down
```

Для серверного обновления установи симлинк `/usr/local/bin/updatetwitch` на `/opt/TwitchDownloader/scripts/updatetwitch`, затем запускай `updatetwitch`.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.
